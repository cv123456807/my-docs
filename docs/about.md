# 关于本项目

## 项目目标

把一组 Markdown 文件变成任何人都能通过浏览器访问的公开网站，并且让"改文档 → 网站更新"这个过程不需要人工干预。

拆开来看是三个小目标：

1. **可写**：内容只用 Markdown，作者不必关心 HTML、CSS。
2. **可建**：任何人（包括 CI 里的机器人）拿到仓库就能一条命令构建出完整站点。
3. **可发布**：构建成功后自动上线，失败时旧版本保持可用。

## 技术组成

| 工具 | 在流程中的位置 | 作用 |
| --- | --- | --- |
| Markdown | 源码 | 用纯文本描述内容，便于版本管理和 diff |
| MkDocs | 构建 | 读取 `mkdocs.yml` 与 `docs/`，生成静态 HTML |
| MkDocs Material | 主题 | 提供导航、搜索、代码高亮、中文界面 |
| GitHub Actions | 流水线 | 在云端按工作流执行安装、构建、上传产物 |
| GitHub Pages | 托管 | 把产物作为静态站点对外提供 HTTPS 访问 |
| Git | 版本控制 | 记录每一次改动，作为触发流水线的信号 |

## 目录约定

```text
my-docs/
├── .github/workflows/deploy.yml   # 流水线定义
├── docs/                          # 站点源码（只有这里的内容会变成网页）
├── report/                        # 课程作业报告与截图
├── mkdocs.yml                     # 站点配置
├── requirements.txt               # 构建依赖的版本范围
└── README.md                      # 仓库门面
```

`docs/` 与 `site/` 的关系值得单独说明：前者是人写的源码，后者是机器生成的产物。产物可以被完整删除再重建，因此它属于"可再生资源"，不进入版本库——这也是 `.gitignore` 里排除 `site/` 的原因。

## 为什么选这套方案

- **没有服务器要维护**：Pages 直接托管静态文件，不需要买主机、配 Nginx、续证书。
- **权限最小化**：工作流只在 deploy 阶段申请 `pages: write` 和 `id-token: write`，构建阶段对仓库只有读权限。
- **失败不污染线上**：`deploy` 依赖 `build`，构建不成功就不会发布，线上始终是上一次成功的版本。
- **过程可审计**：每次发布都对应一次提交和一条 Actions 运行记录，谁在什么时候改了什么一目了然。

## 已知局限

- 只适合静态内容，没有后端逻辑和用户数据。
- 构建在 GitHub 提供的运行器上执行，依赖下载速度受网络影响。
- 项目站点的地址带仓库路径（`/my-docs/`），因此 `site_url` 必须写全，否则资源和链接会错位。
