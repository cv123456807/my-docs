# 使用指南

本页面向"以后要自己改这个站点"的人，包括几个月后的我自己。

## 日常维护五步

1. 修改 `docs/` 目录中的 Markdown 文件。
2. 在本地预览，检查页面、导航和链接。
3. 提交修改并推送到 `main` 分支。
4. 在 Actions 页面查看构建与部署状态。
5. 打开网站，确认内容已经更新。

## 常用命令

```bash
# 创建并激活虚拟环境（Windows PowerShell）
python -m venv .venv
.\.venv\Scripts\Activate.ps1

# 安装依赖
python -m pip install -r requirements.txt

# 本地预览，默认 http://127.0.0.1:8000/
python -m mkdocs serve

# 构建，并让警告直接报错（与 Actions 中完全一致）
python -m mkdocs build --strict
```

`--strict` 这个参数很重要：MkDocs 默认把"链接指向不存在的页面"当成警告，构建仍然成功；加上 `--strict` 后警告会变成错误，构建失败。本地先用它跑一遍，就不会出现"本地好好的、推上去却红了"的情况。

## 新增一个页面

1. 在 `docs/` 下新建 `faq.md`。
2. 在 `mkdocs.yml` 的 `nav:` 里加一行 `- 常见问题: faq.md`。
3. 在需要的页面里用相对路径链接它：`[常见问题](faq.md)`。
4. 本地 `build --strict` 通过后提交。

## 目录与写法约定

| 约定 | 说明 |
| --- | --- |
| 文件名用小写和连字符 | 例如 `getting-started.md`，避免大小写造成的链接失效 |
| 链接用相对路径 | `about.md` 而不是绝对地址，仓库改名后仍然可用 |
| 图片放在 `docs/` 下 | 用 `![](images/xxx.png)` 引用，随构建一起发布 |
| YAML 只用空格缩进 | `mkdocs.yml` 和工作流文件里出现 Tab 会直接解析失败 |

## 排错顺序

遇到"推了但网站没变"，按下面的顺序排查，通常两分钟就能定位：

1. **有没有触发运行**：Actions 页面是否出现新的运行记录。只改了 `report/` 或 `README.md` 不会触发，这是工作流里 `paths` 过滤的预期行为。
2. **运行是否成功**：`build` 和 `deploy` 两个任务是否都是绿色。红色就展开失败步骤读日志，Python 构建失败通常能在日志末尾看到具体文件和行号。
3. **发布是否完成**：`deploy` 任务详情里会给出 `page_url`，这就是本次发布的地址。
4. **浏览器缓存**：用 `Ctrl+F5` 强制刷新，或开无痕窗口对比。

## 设计取舍说明

工作流把"构建"和"部署"拆成两个 job，而不是写在一个 job 里连续执行。这样做的好处是：构建在只有读权限的环境中完成，产出的静态文件作为 artifact 传给部署任务，部署任务才申请写入权限。权限被压缩到最小范围，同时"构建失败"和"发布失败"在记录里可以一眼区分。

接口文档的写法示例见 [API 参考](api.md)，项目背景见[关于本项目](about.md)。
